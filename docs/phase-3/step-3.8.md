## 实现与发现的问题

1. switch 在候选探测前检查目标 profile 和旧默认 profile 的活动任务。受占用时先公开 `waiting_for_idle`，沿用 FIFO、最多八项和五分钟等待上限；等待可取消，候选前后及最终提交仍复核修订、能力、凭据和占用。原先候选先等待自有进程串行锁，导致状态长时间停在 `checking`，无法正确呈现等待原因。
2. 凭据替换/删除等待期间释放凭据操作锁，取得空闲后重新获取锁，并在原有 SQLite/系统凭据补偿事务中复核修订和占用。原先持锁等待时，已准入的排队 worker 需要同一锁才能读取冻结凭据，导致互相等待。竞争者抢先修改/新准入时固定拒绝，不自动重试写入。
3. profile 禁用增加与编辑一致的活动任务拒绝。删除仍因历史快照、默认引用或未完成 operation 返回 `PA_PROVIDER_REFERENCED`；不会删除任务历史。项目 AI 默认只是未来任务的选择元数据，允许原子更新，不替换运行进程/Key；已运行或已准入任务的完整快照保持不变（计划第 6 章的既定约定）。
4. 明确退出先关闭任务、provider 队列和自有候选操作的准入，再取消运行/排队工作，等待任务 worker、provider drain 及模型目录/连接探测候选完成。候选等串行锁也改为可取消。移除任务 worker 固定五秒后提前返回的退出分支；清理完成后才退出。Windows Job 继续在应用异常退出时关闭其自有进程树。
5. `OwnedProcessState` 对模型目录/候选探测使用作用域登记，退出取消所有登记 token；作用域退出才移除登记，确保等待覆盖实际候选关闭及 home 清理。不会枚举或结束外部 Codex 进程。
6. 清空全局默认不再同时清除 `ai_runtime.blocked`。回滚失败时，即使用户清空默认或只做连接测试，新任务仍被拒绝；须成功提交一次明确切换来恢复。运行时清理失败也在任务准入前拒绝，不先产生一个注定失败的新 worker。

```powershell

```

报告只保存固定检查描述、计数、版本、布尔值和固定状态；不保存 Key、prompt、回复、项目路径或原始协议。临时目录在退出后移除，凭据按该隔离数据库中的 profile/版本精确清理；失败清理也由独立 worker 执行，不把强制结束夹具记为正常退出通过。

## 故障与恢复矩阵

| 情况 | 权威结果与恢复方式 | 证据类别 |
| --- | --- | --- |
| 运行任务时编辑/禁用/删除 profile | 编辑/禁用固定 busy；删除固定 referenced；任务快照及实际 A 站请求/Key 不变 | dev/built 真实服务、CLI、双合成 HTTPS |
| 两会话已准入任务 + 切换 + Key 替换 | worker 继续使用旧快照；切换等待两任务空闲；Key 变更后历史配置/凭据修订保持不变；新 B 站使用 B Key | 同上，比较完整历史快照 |
| FIFO 上限/取消 | 八项含运行项，第九项拒绝；取消等待项不取消任务；候选等串行锁也能独立取消 | 真实桌面 + 生产状态机单测 |
| 项目默认更新/修订竞争 | 默认更新只影响未来选择；任务不漂移；profile/global 修订竞争在提交前复核，不自动覆盖 | 真实桌面 + `providers::tests` 修订注入 |
| 候选连接失败 | `unchanged`，旧配置仍可识别，无自动换源 | 真实 CLI，合成 HTTPS 401 |
| applying 探测失败、旧配置重验成功 | `rolled_back`，旧默认保留，恢复证据必须来自对旧完整选择的重新核验 | 三次真实 CLI 探测，合成 HTTPS 请求序列 |
| applying 失败且回滚探测失败 | `rollback_failed` / `configState=error`，阻止新任务；仅做连接测试不能解除阻断，须用户明确切换并成功提交 | 真实 CLI/HTTP 失败序列 + 真实任务准入拒绝 |
| CLI 安装/启动不可信、路由/能力变化 | 在请求或提交前拒绝；不采用替代源；清理失败则阻断新任务 | 既有 owned-process/路由/能力单测及真实网关/隔离验收，范围单列 |
| SQLite busy + 审批/取消 | 写事务拒绝，任务/审批修订和事件/审计不产生部分提交 | 两个真实 SQLite 连接与 IMMEDIATE 锁 |
| 只读写失败 + 启动恢复 | 保留原任务/审批状态；恢复不能写入时不上报成功；解除故障后主动重启恢复为 interrupted | SQLite `query_only`，属于权限写失败注入，不修改用户 ACL |
| 磁盘满 + 审批/恢复 | 真实 `SQLITE_FULL` 拒绝整批；未决审批不变；解除限制后显式恢复 | 临时 SQLite `max_page_count` 与大页写入；不填满物理磁盘 |
| 审计失败 + 取消/启动恢复 | 状态/修订/事件/审计原子回滚；解除注入后恢复一次，多次恢复不重复任务 | 临时 SQLite trigger 注入 |
| IPC 超时/丢失响应、事件缺口和 WebView 重载 | 只停止前端等待；按原 request ID 查同一任务，不重发变更；从权威快照恢复 | IPC transport 单测 + 真实桌面丢失响应/缺口/重载组合；不把主动忽略响应说成实际网络超时 |
| 关闭主窗口/停用 overlay | 常驻启用时 main X 仅隐藏；overlay 停用不取消任务；常驻停用后的 main X 按既定约定退出应用 | 真实 WebView 调用窗口关闭与正式 overlay disable；实际托盘鼠标仍待人工 |
| 明确退出：运行任务 + 等待切换/目录刷新 | 先关闭各准入并取消，随后等待 worker/候选清理；进程结束前 home 已清空，无未结束配置操作 | dev 真实进程；退出前后自有 PID 观测及独立重开核对 |
| 审批等待中应用崩溃 | OS Job 结束自有 CLI；启动时任务 interrupted、审批失效、等待操作结束、home 清理；无网络/任务/审批重放 | built 只终止应用 PID，未使用 `/t` 代替 Job；独立进程两次恢复 |

## 生命周期与运维诊断

服务和持久仓储是任务状态依据，窗口的挂载/可见性和前端等待状态不代表服务端取消或完成。任务取消只报告已接受，终态仍需 `task_get` / 原请求查询确认。

发生 `PA_PROVIDER_ROLLBACK_FAILED` 时：先在 AI 配置页读取当前 profile/原默认和 operation 结果，确认站点/Key/模型/effort，按需修复凭据并刷新能力，再主动执行测试/切换；只有成功的正式 switch 提交才恢复 ready。不得通过前端重载、重发原任务、后台重试或换源清除 blocked。凭据变更、adapter/CLI 身份或能力变化会使旧证据失效，应重新核验。

发生 SQLite busy、权限/磁盘/审计失败时：保留原库及升级备份，解除应用数据目录写入故障或竞争写锁后主动重新启动。启动恢复必须成功写入中断/审批失效与审计，否则存储不可用，不启动任务；不删除原库重建。任务运行中发生存储/清理失败时 owned runtime 阻断新任务，不能仅靠 UI 刷新解除；先排除故障、重启观察自有资源清理和存储恢复，再重新测试/切换，并由用户显式恢复 interrupted 会话、提交新任务。

明确退出可能需要等待自有候选/worker 收尾，不能用“五秒已到”推断已清理。异常杀进程时内存回复/草稿不可恢复；持久任务/审批仅恢复终态与元数据。未决和已 claim 审批不会再次执行。

## 保留边界

默认仍串行执行自有 CLI；多会话/profile 同时准入并排队不代表多个 CLI 同时并行已经验收。物理中文 IME、托盘鼠标、多显示器/热插拔/实时 DPI、ReFS 和其他平台继续按上游记录待验。

补丁 grantRoot 仍受 3.5/3.6 的绑定限制；正文仍只在有界进程内缓存，摘要采集默认关闭。阶段统一 `verify:tasks`、M3 全部用例汇总及阶段 4 移交仍属于 3.9，本步骤不能据此宣布 M3 整体完成。
